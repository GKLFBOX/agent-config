# Public Release Audit

開発リポジトリをそのまま公開しない。
公開用リポジトリを別に作り、allowlistに列挙したファイルだけを写して組み立てる。
除外リスト方式では新規ファイルが既定で公開され、除外し忘れがそのまま漏洩になる。

## 1. allowlistを書く

公開してよいファイルを列挙し、開発リポジトリ側の公開対象外のパスへ置く（既定は`docs/public-allowlist.txt`）。
公開ツリー側へ置くと、公開判断という内部運用がそのまま公開される。

- 1行1パス、リポジトリルートからの相対、区切りは`/`。
- `#`で始まる行と空行は無視される。
- ディレクトリを書くと配下すべてを許可する。

更新公開では、開発リポジトリに増えたファイルを一覧と突き合わせ、公開するものだけ追記する。

## 2. 公開ツリーを組む

allowlistに従って別ディレクトリへ写し、`git init`してコミットする。
開発リポジトリの履歴は持ち込まない。

コミットメッセージへ内部事情を書かない。
非公開のリポジトリ名、ディレクトリ名、内部運用手順、検証結果の宣言は、公開履歴に残す価値がない。
「秘密はない」という宣言は何も守らず、将来矛盾しうる。

`.gitignore`は開発リポジトリから丸写ししない。
公開ツリーで実際に生成されるものだけを書く。

## 3. 監査する

```powershell
& <スキルのパス>/scripts/Invoke-PublicReleaseAudit.ps1 `
    -RepoPath <公開ツリー> `
    -Allowlist <allowlistのパス> `
    -Denylist <denylistのパス>
```

終了コードは、全PASSで0、要確認ありで1、実行不能で2。
`-Denylist`は任意で、省くと個人識別子の観点をスキップする。
雛形は同梱の`denylist.example`にある。

スクリプトが見るのは8観点である。

| 観点                   | 判定                     |
| ---------------------- | ------------------------ |
| 秘密情報               | PASS / 要確認            |
| ローカルパス           | PASS / 要確認            |
| 個人識別子             | PASS / 要確認 / スキップ |
| allowlistとの差分      | PASS / 要確認            |
| 無視漏れ               | PASS / 要確認            |
| 巨大ファイル・バイナリ | PASS / 要確認            |
| 全コミットの著者       | 情報                     |
| 履歴の広がり           | 情報                     |

「情報」は機械では合否を決められない。出力を読んで判断する。

## 4. 判断が要る観点

スクリプトは扱わない。
次の4つを人が読んで判断する。
1と3は実際に混入が見つかった箇所であり、機械判定だけでは両方素通りする。

1. **コミットメッセージ全件**。`git log --format='%H %s%n%b'`を読み、非公開のリポジトリ名、ディレクトリ名、内部運用手順、検証結果の宣言が混じっていないか見る。
2. **READMEとソースコメント**が内部事情を書いていないか。
3. **`.gitignore`**に非公開ツールの名前が残っていないか。開発リポジトリからの丸写しで混入する。
4. **grepのヒットを残してよいか**。ヒットが常に誤りとは限らない。ソースへ固定で入る名前は、残す判断もありうる。

## 5. 報告する

観点ごとの結果、判断が要る観点の所見、公開してよいかの結論を出す。
結論はスクリプトの終了コードではなく、実行者が書く。

pushはユーザーが行う。

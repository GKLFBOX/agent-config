# 簡潔な日本語執筆（Concise Japanese Writing）

日本語のソースコメント・ドキュメントを簡素に保つ行動指針。実装における karpathy-guidelines に対応する執筆版。

## 併用する規範

設計書・実装計画など、段落や節で論証を組み立てる日本語の技術文書を書く／推敲するときは、作業前に `../japanese-tech-writing/SKILL.md` を読む。ソースコメント、内部JSDoc、短い注記には適用しない。

## 核となる原則

**自明な説明を削り、判断に必要な情報だけを残す。** レビュアーの時間が最も希少な資源。

残すのは「コードで表せないもの」—— なぜ(why)・非自明な制約・落とし穴・警告。コードと型で自明な what/how は書かない。説明過多はレビュー負荷になる。

**例外（説明を厚くしてよい）:** 読者がソースを読まない文書（公開 API リファレンス、外部向けチュートリアル）。運用・移行手順、障害対応 Runbook、セキュリティ注意、ADR の設計理由も「削る」対象ではない。迷ったら「削らない境界」節へ。

## 1. コード・型で自明なことは書かない

レビュー時に型・名前から即読める事実の再説明を削る。

```ts
// Before
let attempt = 0; // 実行回数を数えるカウンター
const url = base + path; // base と path を連結して URL を作る
// After（コードが語る。削除）
let attempt = 0;
const url = base + path;
```

既定値やパラメータ名の言い換えも削る（内部 JSDoc）。`@param maxAttempts 最大試行回数。既定値は 3` の「既定値は 3」はシグネチャにある。公開 API では既定値を残してよい。

## 2. 履歴語り・時点語を残さない

「以前は」「今回」「新しく」「変更後」「暫定的に」は時間とともに矛盾化する。変更の履歴は git が持つ。

```ts
// Before
// 以前は同期版だったが、今回リトライ対応のため非同期に変更した
// After（時点語を外し、現在も効く制約を why として残す）
// リトライ時も呼び出し側の Promise チェーンを壊さないため非同期で返す
```

## 3. 冗長な言い回しを削る（日本語特有）

不要語を削る（elements-of-style "Omit needless words" の日本語適用）。

- 冗長語尾: 「〜することができます」→「〜できる」／「〜となっています」→「〜」
- 名詞化: 「〜の実行を行う」→「〜する」／「設定するためのもの」→「設定用」
- 翻訳調・空語: 「〜において」「基本的に」「まず初めに」を削る
- 保険表現: 「必要があります」「可能性があります」は確度を確認し、確かなら断定。曖昧なら条件を書く（「〜の場合に発生」）
- 接続語過多: 「また」「なお」「ただし」「そのため」の連発を減らす
- メタ説明: 「この節では〜」「以下では〜を説明します」は見出しで足りるなら削る
- 敬体過剰: コメントは常体（だ・である／体言止め）。自明な主語は消し、動作から書く

## 4. 同じ内容を2度書かない

説明は1箇所に置き、他所からは参照する。JSDoc・本文概要・別表で同じ概念を繰り返さない。

## 5. 具体・肯定・能動で書く（elements-of-style）

- 具体語 > 曖昧語（「適切に処理」→「例外を捕捉して `ValidationError` を返す」）
- 肯定形 > 否定形（「〜しないわけではない」→「〜する」）
- 能動 > 受動（「〜が行われる」→「〜する」）
- 要点は文末に置く。ただし WARNING・禁止条件は先頭に置く

## 削らない境界（重要）

簡素化は「価値あるコメントの削除」ではない。次はコードで表せない。**残す。**

- **なぜ(why)**: 実装を選んだ理由、他案を採らなかった理由
- **落とし穴・警告**: 副作用、二重実行、スレッド安全性、既知の制約
- **非自明な前提**: 呼び出し順序、外部仕様への依存、単位・範囲の約束
- **参照**: 仕様・Issue・論文へのリンク（出典）

削る前に、その行が上記を含まないことを確認する。git にしか無いと危険な「現在も効く制約」は残す。

```ts
// これは残す（コードからは読めない warning）
// リトライ用 callback。fn は複数回呼ばれる。
// 課金など二重実行してはいけない副作用には使わない。
```

## レッドフラグ（見たら「削る／具体化する／why に変える」）

| 書き出し・語法                                               | 対処                                      |
| ------------------------------------------------------------ | ----------------------------------------- |
| 「このメソッドは〜します」                                   | 主語を消し動作から書く。自明なら削除      |
| 「〜することが可能です」「〜となっています」「〜を行います」 | 短縮・動詞化                              |
| 「まず初めに」「基本的に」「〜において」                     | 空語。削る                                |
| 「適切に」「必要に応じて」「柔軟に」「各種」                 | 曖昧語。具体条件に置換                    |
| `x++` に「x を1増やす」                                      | 逐語コメント。削る                        |
| 「以前は」「今回」「新しく」                                 | 時点語。削るか why に変える               |
| 同じ説明の2箇所目                                            | 1箇所へ集約し、他所は参照                 |
| 既定値・型の再説明                                           | シグネチャにある。削る（公開 API は例外） |

**判定基準:** 書いた各行に「型・名前・git で即分かるか？」を問う。分かり、かつ why・警告・運用注意でなければ削る。
